# Implicit parallelism in Loom

Loom applies implicit CPU parallelism to hosted Float32 elementwise operations `Vector_Add`, `Vector_Sub`, `Vector_Mul`, and `Vector_Scale`, and to a restricted class of large fixed-array map loops. Existing Loom programs use ordinary calls and loops; they need no `Parallel_For`, task handles, or annotations.

The compiler lowers supported operations to the Loom runtime on hosted targets. The runtime divides large ranges into dynamically claimed contiguous chunks and executes them on its persistent worker pool. The runtime requires at least eight chunks; the compiler additionally requires a 524,288-element fixed-array map (16 chunks at its current grain size) before selecting that transformation. Small ranges stay sequential. The pool is shared with Loom tasks, and an operation falls back to sequential execution when called from a Loom worker or while explicit Loom tasks are outstanding. Bare-metal code keeps the sequential compiler lowering.

These operations are safe to parallelize because each output element reads only the corresponding input element or elements and writes one output element. Exact in-place aliases such as `Vector_Add(A, B, A, N)` remain independent by element. Partial input/output overlap can create loop-carried dependencies, so it is detected and processed sequentially. The runtime also checks null pointers, operation identifiers, and the byte-count overflow before touching memory.

The automatic loop transformations support compile-time inclusive `1..N` ranges that exactly cover a fixed array. A fill loop assigns a constant to each element; repeated-byte integer constants are lowered to `memset`. An elementwise loop can contain multiple ordered indexed writes to same-sized, non-volatile local fixed arrays. Its scalar expressions can use same-index reads, the induction variable, primitive scalar operators, wrapping arithmetic, and known pure math intrinsics. Later writes in an iteration may read earlier same-index writes, preserving source order. The current profitability gate is 524,288 elements. Unknown calls, cross-index reads, dynamic bounds, pointer-based containers, globals, and nested control flow are excluded from this transformation.

This remains a narrow implementation. Loom does not automatically parallelize arbitrary `Loop` bodies, reductions, or operations that call user code. The optimizer reports actual selected transformations; the legacy loop-shape candidate notice is informational and does not imply a transformation. Broader cases require compiler-proven effects, alias and dependence analysis, and clear semantics for traps, floating-point reassociation, cancellation, and nested parallel work. `Parallel_For` remains an explicit facility.

Performance depends on input size, processor count, and memory bandwidth. On one Apple Silicon host, the 4-million-element vector-add comparison was within measurement noise of optimized C and Rust; it did not show a repeatable win over C. Parallel execution is not a promise that every program runs faster. Keep a sequential implementation available for operations without a proven independence and profitability test.

## Remaining work

The current transformations are deliberately narrow and do not make arbitrary loops parallel. The compiler still needs reusable effect summaries (reads, writes, calls, pointer escapes, allocation, I/O, synchronization, and traps), alias/dependence analysis for general loop bodies, and explicit contracts for reductions, overflow, floating-point determinism, cancellation, and nested parallel work. The current threshold is conservative but host-dependent; broaden it only after repeatable per-target measurements. Race testing, task interaction, oversubscription, and scaling comparisons should remain part of validation for each new transformation.
