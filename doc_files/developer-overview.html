Systems Architecture & Internals

Developer overview

A technical guide for systems engineers: memory layout, safety guarantees, deterministic cleanup, LLVM lowering, volatile hardware I/O, C FFI interop, and semantic graph generation.

Memory model & representation

Loom operates with an explicit, unabstracted memory model. There is no garbage collector, no reference counting, and no hidden heap allocator. Memory allocation is strictly under programmer control:

ConstructPhysical Memory Layout & Semantics
ScalarsScalar types (Signed_32, Float_64, etc.) map directly to native machine registers or stack slots aligned to their natural width.
Fixed Arrays (T Array[N])Contiguous, flat memory block allocated on the stack (for local declarations) or in the static data segment (for global declarations). No heap header or hidden metadata overhead.
Slices (T Slice)A 16-byte fat pointer struct containing a 64-bit pointer to element 1 and an unsigned 64-bit integer element count. Slices are non-owning views and do not allocate or free memory.
Pointers (T Pointer)Direct 64-bit (or 32-bit on ARM Cortex-M) raw memory address. Uninitialized pointers default to Null (zero).
RecordsContiguous struct layout matching target ABI alignment rules. Field order is preserved. Pass-by-value and return-by-value copy entire struct bytes.

Safety guarantees & undefined behavior

Loom balances bare-metal hardware access with deterministic runtime safety bounds:

  • Bounds Safety: Array, slice, and string indexing are strictly bounds-checked at runtime. Accesses outside [1, Length] trigger an explicit processor trap instruction (e.g. brk #1 on ARM64 or ud2 on x86_64), preventing memory corruption or arbitrary code execution. When index ranges can be proven safe at compile time, the optimizer eliminates bounds checks entirely.
  • Pointer Validity: Raw pointers are unmanaged. The compiler proves type compatibility but cannot verify arbitrary runtime lifetime or alignment. Always verify Ptr != Null prior to calling Deref(Ptr).
  • Integer Arithmetic: Fixed-width integer operations wrap on overflow using two's complement rules. Division or remainder by zero, or shifting by counts greater than or equal to the operand width, are diagnosed by the compiler when constants are known.
  • Floating-Point Strictness: Floating-point calculations conform strictly to IEEE 754 without aggressive fast-math contractions, guaranteeing reproducible rounding behavior across builds.

Deterministic cleanup with Ensure

The Ensure { <statement> } construct guarantees that cleanup logic executes when exiting a scope or procedure. Statements execute in strict Last-In, First-Out (LIFO) reverse order of registration:

Block Open_Device
Implements
    Ensure { Release_Hardware() }
    Ensure { Flush_Buffers() }
    If (Fault_Detected())
        Exit              # Flush_Buffers() runs first, then Release_Hardware()
    End If
    Write("Device ready for operations...")
End Open_Device

Compiler Lowering: The loomc frontend lowers Ensure statements into a unified landing pad in LLVM IR. Whether a block returns normally via reaching the end, returns early via Give <Expr>, or breaks via Exit, the control flow graph branches through the cleanup chain in reverse sequence before the final return instruction.

Why one-based indexing

Loom uses 1-based indexing for all arrays, slices, and strings. This design decision serves several systems engineering goals:

  • Elimination of Off-by-One Errors: In 1-based indexing, the index of the last element is always identical to the collection's Length. Loop headers write naturally as Loop while (I <= Arr.Length) without requiring manual Length - 1 subtractions.
  • Direct Mathematical Mapping: Matrix algorithms, DSP transforms, Fourier analysis, and algorithmic specifications (such as discrete mathematics and signal processing textbooks) naturally index vectors and matrices from 1 to $N$.
  • Byte Strings: String indexing selects the $k$-th UTF-8 byte as an Unsigned_8 value, where Str[1] is the leading byte.

LLVM Optimization Passes

When compiling with loom build --release, the compiler runs an aggressive LLVM optimization pipeline:

Optimization PassTechnical Mechanism & Benefit
Function InliningEliminates function call overhead for small blocks and concise routines (Produces (A + B)), allowing inter-procedural constant propagation.
Loop VectorizationDetects contiguous array and slice loops, generating SIMD instructions (NEON on Apple Silicon ARM64, AVX/SSE on x86_64).
Bounds-Check EliminationStatically proves loop indices remain within [1, Length], stripping redundant bounds-checking branches from loop bodies.
Dead-Code StrippingRemoves unused block definitions, unreferenced variables, and dead branches across modules.

Inspecting the Optimization Report

Run the optimization report flag to see exactly which loops were vectorized and which bounds checks were removed:

loom build --release --opt-report

Volatile hardware I/O & memory barriers

Device drivers and bare-metal systems require reading and writing hardware peripheral registers that are mapped into memory addresses. Standard memory reads and writes could be reordered or eliminated by an optimizing compiler. Loom provides explicit volatile intrinsics:

# Volatile reads: cannot be cached or hoisted
Status = Vol_Read_32(0x4000C008)

# Volatile writes: cannot be eliminated or reordered
Vol_Write_32(0x40014004, 5)

LLVM Representation: These intrinsics emit LLVM instructions marked with the volatile attribute (e.g. load volatile i32, ptr %addr), creating strict compiler memory barriers that force memory operations to occur exactly where specified.

C Foreign Function Interface (FFI)

Loom interfaces directly with C code and operating system system libraries using the Extern Block declaration:

Extern Block puts
    Takes
        S : String
    Produces Signed_32
End puts

Block Main
Declares
    Status : Signed_32
Implements
    Status = puts("Calling C standard library puts directly from Loom!")
End Main

When building, the Clang linker links external C object files or libraries automatically against your Loom executable.

Architectural dependency graphs

The Loom toolchain can inspect and visualize project architecture from compiler semantics without compiling native code:

# Generate Mermaid call dependency graph
loom graph --view calls --format mermaid

# Generate JSON architectural model
loom graph --view data --format json

Mermaid diagrams are written to loom-deps.mmd. You can preview these graphs directly in VS Code or render them in GitHub Flavored Markdown.
